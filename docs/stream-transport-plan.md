# HTTP stream: дедлайн, лимит и отмена — варианты реализации

Статус: предложение для обсуждения, **реализация не начата**.

- GitHub: https://github.com/lad-tech/nsc-toolkit/issues/185
- Источник: https://glab.lad24.ru/e-ai/codebase/-/work_items/3596

## Что уже есть

- `Client.request` вычисляет абсолютный `baggage.expired`.
- HTTP-адрес запрашивается через брокер с отдельным таймаутом 1000 мс.
- `http.request({ timeout })` задаёт socket timeout, а не общий дедлайн.
  Обработчика `timeout`, закрывающего запрос, сейчас нет.
- Для streamed response клиент возвращает `IncomingMessage` сразу после заголовков.
  Ошибка после этого должна приходить через поток, а не через уже завершённый Promise.
- `Service` отдаёт входящий `IncomingMessage` непосредственно обработчику,
  без ограничения размера.
- `createMethodContext` уже создаёт `signal` дедлайна и освобождает таймер,
  в том числе после завершения возвращённого потока.
- Service middleware вызывает клиент с одним аргументом и потеряет новый
  аргумент с настройками, если оставить текущую обёртку без изменений.

## Вариант A: локальные изменения существующего транспорта — рекомендуется

Никаких новых зависимостей, базовых классов или реестров транспортов.
Изменения остаются в `Client`, HTTP-части `Service`, `MethodContext`
и существующих интерфейсах. Небольшой приватный helper допустим, если он
действительно убирает повторение освобождения ресурсов.

### Предлагаемый API

Названия пока не утверждены:

- Второй необязательный аргумент метода клиента:
  `client.parse(payload, { signal })`.
- Один тип `CallOptions` с необязательным `signal`.
- Четвёртый необязательный аргумент `Client.request` — эти же настройки.
  Старые вызовы с тремя аргументами остаются рабочими.
- В существующем `MethodOptions.useStream`:
  - `maxRequestBytes?: number` — лимит входящего потока в байтах;
  - `cancelOnDisconnect?: boolean` — серверная отмена по разрыву ответа.
- В контексте service middleware — необязательные `callOptions`,
  которые передаются клиенту вместе с `params`.

`AbortSignal` не является частью payload, JSON-схемы или baggage:
это локальный объект управления одним вызовом.
По умолчанию лимит не включён, отмена по disconnect выключена.
Если лимит указан, принимать только положительное безопасное целое.
Новый глобальный конфиг, env-переменные и несколько уровней override не нужны.

### Клиент: один дедлайн на весь HTTP-вызов

1. Использовать уже вычисленный абсолютный `expired`, не запускать новый
   полный timeout после получения адреса.
2. Создать один управляемый жизненный цикл вызова: таймер дедлайна,
   подписка на внешний signal и идемпотентное освобождение ресурсов.
   Проверять уже отменённый signal до побочных действий и повторно после
   поиска адреса.
3. Поиск адреса ограничить оставшимся бюджетом и существующим максимумом
   1000 мс. Отмена должна немедленно завершать ожидание клиента; сам внутренний
   запрос к брокеру может дожить до ограниченного таймаута. Обработать его
   позднее завершение/ошибку, HTTP после отмены не запускать.
4. При дедлайне/отмене закрывать HTTP-запрос, response и принадлежащую этому
   вызову отправку входного потока; не оставлять producer подключённым
   к закрытому соединению.
5. До выдачи ответа отклонять Promise. После выдачи `Readable` уничтожать
   поток с ошибкой. Слушать ошибки/преждевременное закрытие тела и для JSON,
   и для streamed response; исключить unhandled rejection в async callback.
6. Снимать таймер и abort-listener после завершения/ошибки/закрытия тела,
   а не в `finally` функции, которая возвращает поток после заголовков.
   `unref()` не заменяет очистку.

Проверка явного `signal` для NATS должна происходить до обращения к кешу
или отправки сообщения: вернуть понятную ошибку неподдерживаемого транспорта.
Обычные NATS-вызовы и их таймауты не менять. Это относится и к внутреннему
request/reply в монолитном режиме; stream-вызовы там по-прежнему используют HTTP.
Для HTTP проверить отмену до cache hit и пересчитывать оставшийся бюджет после
асинхронных подготовительных операций. Таймауты самого cache adapter не
перепроектировать в рамках этой задачи.

### Сервер: лимит без буферизации

- Один маленький байтовый `Transform` перед handler: считать `chunk.length`
  и передавать chunks дальше с обычным backpressure.
- Ровно N байт допустимы; chunk, пересекающий лимит, не отдавать обработчику.
- `Content-Length` можно использовать для раннего отказа, но не вместо
  фактического подсчёта.
- Не добавлять отдельный `data`-listener: он переключает поток в flowing mode.
- Ошибку лимита обрабатывать на уровне HTTP-handler независимо от того,
  перехватил ли её пользовательский handler.
- До отправки заголовков вернуть HTTP 413 с существующим JSON-конвертом
  ошибки. Клиент должен распознавать ошибочные HTTP-статусы, а не считать
  любой статус кроме 500 успешным бинарным ответом.
- Остановить дальнейшее чтение и обработку, безопасно завершить ответ,
  затем закрыть соединение. Нельзя сначала уничтожить `IncomingMessage`
  через `pipeline`, потерять сокет и обещать доставку JSON-ошибки.
  Не вычитывать неограниченный остаток тела.

Ограничение потокового протокола: если handler уже начал streamed response
до окончания загрузки и лимит превышен позже, заменить отправленные заголовки
на 413 невозможно. В этом случае оборвать ответ с ошибкой. Для гарантированного
413 handler должен закончить чтение request до начала ответа; буферизовать весь
request ради этой гарантии не предлагается.

### Сервер: совместить disconnect с существующим сигналом

- Минимально расширить `createMethodContext(expired, externalSignal?)`:
  тот же controller получает дедлайн и opt-in сигнал закрытия HTTP-ответа.
  `dispose` освобождает таймер и внешнюю подписку.
- Для `cancelOnDisconnect` слушать `ServerResponse.close` и отменять только
  при `!response.writableFinished`. Не использовать обычный `request.close`
  как признак отмены: завершение чтения запроса нормально.
- Подписка должна существовать до завершения HTTP-ответа, включая передачу
  возвращённого потока; нормальный `finish` только освобождает ресурсы.
- При disconnect останавливать и передачу response stream, если она идёт.
  Сохранять текущую семантику дедлайна для методов без opt-in.
- Отмена бизнес-логики кооперативная: handler/адаптер должен использовать
  `context.signal`. Принудительно остановить произвольный Promise нельзя.

Это не требует протокола удалённой отмены, передачи signal через NATS
или автоматического наследования сигнала всеми DI-зависимостями.

## Вариант B: те же изменения, но прямой аргумент `signal`

API: `client.parse(payload, signal?)`, затем `Client.request(..., signal?)`.
Middleware передаёт этот аргумент и при необходимости показывает `signal`
в контексте. Серверная часть и таймеры такие же, как в варианте A.

- Плюс: немного меньше типов и вложенности для одной настройки.
- Минус: при появлении ещё одной настройки вызова понадобится менять
  форму API или добавлять позиционные аргументы.

Разумный вариант, если принято принципиально не расширять настройки вызова.
Вариант A добавляет всего один маленький тип и чуть удобнее читается.

## Вариант C: переписать HTTP-клиент на встроенный `fetch`

AbortSignal у fetch покрывает и получение ответа, и чтение тела.
Но потребуется адаптация Node/Web streams, особенности отправки потокового
тела (`duplex`), проверка поддерживаемой версии Node и повторная проверка
всей текущей семантики HTTP-вызовов. Поиск адреса и серверный лимит всё равно
придётся решать отдельно.

Внешних npm-зависимостей нет, но объём изменений и риск регрессий больше.
Для этой задачи не рекомендуется.

## Что не решает задачу

- Только `request.setTimeout`: это не абсолютный дедлайн; активный поток
  может продолжаться неограниченно.
- Только `Promise.race`: завершает ожидание, но не закрывает соединения
  и не останавливает чтение.
- Только `Content-Length`: не покрывает chunked upload.
- Только серверный signal: не гарантирует клиентский дедлайн.
- Универсальный cancellation/transport framework: избыточен.

## Проверки будущей реализации

Часть сценариев нужна с настоящим локальным HTTP-сервером, поскольку мок
`http.request` не проверяет закрытие сокета и порядок событий Node streams.

- Дедлайн и abort: до вызова, во время поиска адреса, до заголовков,
  посередине JSON-тела и streamed body, во время upload.
- Позднее завершение поиска адреса не запускает HTTP после отмены.
- Нормальный ответ не отменяет signal; disconnect отменяет только opt-in
  методы; дедлайн продолжает работать.
- Лимит N/N+1, несколько chunks, chunked upload без Content-Length,
  ранний отказ по длине и корректный 413 на клиенте.
- Ошибки входного/выходного потока, backpressure, ранний выход handler,
  разрыв соединения и отсутствие необработанных ошибок.
- Очистка таймеров/listeners на всех путях; независимость параллельных вызовов.
- Middleware не теряет call options; старые клиенты работают без изменений.
- NATS без signal работает как раньше, с signal явно отклоняется.

## Границы работы

После согласования — один небольшой feature PR с тестами и документацией,
без общего рефакторинга. Этот PR пока содержит только план.

Шаблон сгенерированных клиентов находится в отдельном `nsc-cli`:
понадобится отдельное согласованное изменение генератора, передающее
необязательный аргумент. Старые сгенерированные клиенты сохранят совместимость,
но не смогут принимать signal до обновления/регенерации.
В этом репозитории можно показать API на существующем примере клиента.
Ни генератор, ни приложение-потребитель в текущую работу не включены.

Перед реализацией согласовать форму аргумента (A или B) и имена двух
серверных настроек. Выпуск пакета и отметка версии в исходной задаче —
только после реализации и проверки, не в рамках планирования.
